# Аудит хранения и передачи данных BBSC/serverless — 03.11.2026

Статус: анализ текущего рабочего дерева, без runtime правок, сборки, деплоя и изменения сейвов.
База эксперимента: BBSC6b6abc2 / BBGL8977cf3 плюс сохранённые незакоммиченные
исправления исходной разработки. Старые study-документы использованы как история,
выводы проверены по текущим определениям и потребителям.

## Семантика, которую сохраняем

Первый подтверждённый Зовущий становится владельцем мира; после завершения роли
возможна смена хозяина без перезапуска. Во время визита мир хоста определяет
состояние окружения; собственные NPC-квесты, персонаж, лут и Сон гостя остаются
личными. Боссы, двери, шорткаты и лампы добавляют разрешённый общий прогресс дома.
Чаши имеют отдельную идентичность; одинаковая карта не означает одно подземелье.
Игра может перезаписать живые таблицы и инвентарь во время загрузки.
Загрузка, смерть, закрытие сокета и таймаут не означают выход игрока.
Миграция работающего мира не нужна. Следовательно, репликация полного игрового
мира на все узлы для назначения нового хозяина не требуется.

Нельзя считать разные представления одного флага дубликатами по значению:
собственное исходное, заимствованное текущее, накопленное разрешённое изменение
и подтверждённо сохранённое — разные стадии операции восстановления.

## Измерения и границы

Read-only metadata/JSON-size на экспериментальном профиле ПК после последнего
прогона: party-journal3077B, state591B, history32, results37 суммарно по двум
участникам. Каталоги BBSC: own-world123981B/1 файл, item-ledger28B/1,
shared-progress20748B/2, guest-items0 файлов. Это размер файлов данного прогона,
не верхняя граница, не измерение RAM и не доказательство ненужности журналов.
Содержимое сейвов не читалось. Секреты и тела заявок не выводились.

Синтетический расчёт существующего формата: WorldFlags1018B + native envelope13B
=1031B; после base64 и типичного JSON/HMAC-заголовка1634B с TCP length-prefix,
без VPN/IP/TCP overhead, ACK и повторов. Это расчёт формата, не замер канала.

## Высокий приоритет: убрать лишнюю работу без смены правил коопа

### 1. Диагностические флаги предметов хоста

Источник: bloodborne_re.cpp5960–5984, SendBbscFlagSnapshot6427,
LogBbscHostWorldFlagsDiff6793, ApplyBbscGuestLootView7806.
Обычный WorldFlags несёт40 групп:30(kind1/6/7) применяются к миру,10(kind5)
используются только для diagnostic diff. Личный лут строится из собственных
флагов/guest-items, а не из kind5 хоста. SharedProgress берёт лишь индексы0..9.

Рекомендация: kind5 хоста сделать опциональной диагностикой; production пакет
оставить30 групп. Это25% содержимого групп; при прежних фиксированных чанках
5×1018→4×1018B, то есть20% WorldFlags-пакетов. Не20% всего игрового трафика.
Нужен новый согласованный version/layout: старый приёмник требует5 частей.
Собственные kind5/guest-items/own-world не удалять.

### 2. Status: убрать поля без удалённого потребителя и повторы

Источники: compat.py66–71,174–175,301,333–336; engine.py342–347,404–406.
Поиск по текущему production party-коду: из remote signs.body читается sign;
placement, native, relay_id в status не читаются. Native state нужен локальному
контролю release/recovery. relay binding использует отдельные native_id и
connection из envelope, поэтому удаление status.relay_id не удаляет эту защиту.

Сейчас весь status рассылается каждые120ms (~8.3/s), native публикуется каждые
250ms, sign часто неизменен; sign содержит большой opaque SummonData. После
успешного join объявление также может оставаться в local_status.
Рекомендация: локальные native поля оставить локальными; sign передавать по
изменению, удаление sign — явно; короткое подтверждение актуальности/обновление
при переподключении. Не прекращать heartbeat без изменения проверки freshness12s.
Нельзя использовать heartbeat для автоматического освобождения world owner.

### 3. Получатели BBSC: активная сессия вместо всего приглашения

Источник: engine.py414–427, compat.py170–176, bbsc_relay.cpp330–422.
Каждый relay frame идёт всем roster кроме себя; native фильтры отбрасывают
чужие session/world сообщения уже на принимающей стороне. Лишний узел также
попадает в ожидание ACK всей очереди. Для группы5 при активных2:4 получателя
вместо1. Для таких сообщений адресация сокращает число копий на75%.
Это не оценка общей экономии и не сокращение требуемых consensus ACK.

Нужна классификация: world/scaling/progress — текущие гости; join bootstrap —
также допущенный гость; placement/объявления — ещё ищущие игроки; адресные
ответы — цель; life/register/leave — участники нужной сессии. Нельзя просто
заменить roster на joined: это потеряет данные до завершения JoinRoom.

### 4. Запись всего party-journal на каждый relay frame

Источник: engine.py26–32,350–360. После каждого нового relay sequence вызывается
persist(): сериализация всего JSON + flush/fsync + replace. Даже для повторяемого
снимка мира это происходит до transport ACK. Участники control state не менялись,
но журнал группы снова записан полностью.

Рекомендация: отделить durable решения группы от приёма gameplay/BBSC кадров.
Для повторяемых снимков — sequence/очередь в RAM и resync по новой connection
incarnation; для одноразовых действий — отдельный компактный durable журнал
принятия/результата, с явной гарантией crash/replay. Бatching допускается только
после определения окна потери. Нельзя просто убрать fsync и сохранить обещание
дедупликации между рестартами. Текущий ACK означает ingress, не native apply;
exactly-once native эффекты и сейчас не обеспечены.

### 5. Неизменившиеся снимки мира и повторные перезаписи

Источники: TickBbscWorldFlagsBroadcast6472, SendBbscFlagSnapshot6427,
OnBbscWorldFlagsPacket22962, ApplyBbscHostWorldFlags6657.
Раз в секунду идут полный текущий блок и ещё1 блок; первые20s/новый участник —
ещё4 блока. Содержимое групп не сравнивается с прошлой отправкой. Отсутствующие
группы и неиспользуемый хвост фиксированного чанка тоже занимают место.

Рекомендация: полный baseline при join/recovery, затем dirty groups с версией
baseline/карты/dungeon/поколения; короткое подтверждение unchanged; явный запрос
полного снимка при пропуске/неизвестной базе. Сохранить pending admission bootstrap.
У receiver готовность/свежесть должна учитывать неизменившийся подтверждённый
снимок, иначе нынешняя граница6s начнёт отвергать корректное состояние.
Части ключевать map+snapshot+chunk+dungeon+revision, не только типом сообщения.

При применении сейчас считаются отличия, но memcpy выполняется и для одинаковых
групп. Можно строить итог после personal masks, сравнивать и писать только
изменившиеся байты/группы. Один лишь last received snapshot ID не разрешает
пропустить применение: native загрузка могла заменить таблицу, та же baseline
должна примениться к новому load generation. Дальний WORLD_SYNC_ALL нельзя
просто выключить: соседние/другие области ранее давали ошибочные world events.

## Средний приоритет: меньше представлений и периодических записей

- engine.py298–333: proposal содержит base+op+next; весь proposal повторяется в
  prepare/commit/final. tx и accepted дополнительно хранят его копии. Можно
  передавать base revision/hash+op+result hash, затем proposal ID/phase, с full
  snapshot/catch-up при recovery. Ввести проверяемый canonical state hash,
  сохранить атомарность, единогласие, accepted и воспроизводимость transition.
  completed/results/history не просто мусор: очередь поздних наблюдателей требует
  результатов;32-entry cache уже исправлял потерянный ACK. Не убирать механически.
- compat.py390/415: каждые50ms deepcopy state, сравнение, затем ещё одна копия.
  Сначала проверять final revision; копировать только при изменении. Это CPU/RAM
  allocation, не сетевой трафик. Не обращаться к изменяемой state без lock.
- bloodborne_re.cpp6400/23002: bbsc_world_ready для обычных карт записывается,
  но не имеет production reader; канонический источник — bbsc_world_blocks.
  Удаляемый кандидат на одну копию порядка8KB. Dream-ready используется, его
  нельзя удалить аналогично. Бесполезные self.acquiring/self.recovering в compat
  тоже кандидаты на уборку, но эффект мал.
- BbscWorldSnapshot6386 хранит64×125=8000B для обычного блока с40 группами.
  При30 группах полезны3750B; можно разделить map/Dream layouts. Осторожно с
  copies через locks и lifetime. Усложнение не оправдано только ради десятковKB.
- TickBbscSharedProgress14817 и WriteBbscPendingProgress14670: каждые10s заново
  пишется коллекция; WriteBbscTripJournal тоже сериализуется без dirty guard.
  Ввести revision/dirty и писать только изменения, сохранив flush на menu/leave,
  recovery pending и retirement только после успешного native save.
- SharedProgress каждую секунду копирует все8KB snapshots и заново OR-ит kind1.
  Копировать только нужные10 групп и учитывать последнюю обработанную revision.
  При новом snapshot kind1 мог измениться/сброситься: заменить текущий shared
  прогресс новым целиком нельзя, он накапливает разрешённые достижения поездки.
- JSON/base64: binary framing уберёт base64 expansion(~33% от binary bytes)
  и verbose keys. На показанном синтетическом кадре1634→1031B — максимум37%
  до нового binary header, HMAC, ACK. Нельзя обещать37% всего трафика. Протокол
  версионировать, native UDP не переносить в reliable ordered control stream.
- Логи research/inventory census уже имеют SHADPS4_BBSC_RESEARCH guard; мод
  описывает default=false. Это режим диагностики, не необходимость коопа.
  Отключение подробных логов допустимо, сохранять essential errors/lifecycle.

## Что не удалять и почему

- Own-world: native save читает live event table; после заимствования мира и
  crash нужен независимый сохранённый оригинал. Ссылки на память игры недостаточно.
- Guest loot: receipt взятого предмета между мирами/rejoin; полный инвентарь
  не доказывает факт получения (предмет потрачен/продан/передан NPC).
- Item ledger: Given/Owed, lot/getFlag/code/count и trip minima различают
  «не выдано», «получено», «законно потрачено», «потеряно при native load».
  Trip journal v2 уже передал item/home-award записи в ledger — не удалять
  две оставшиеся структуры по ошибочному предположению, что обе хранят предметы.
- Personal talk journal и NPC masks: общие world bits не дают права применить
  чужой квест или повторно выдать подарок. Правильны и значения0, не только1.
- Progress: временный вид мира и разрешённый перенос домой — разные политики.
  Полное присвоение host save уменьшило бы код, но меняет концепцию игры.
- Param tables: мод использует live repository NpcParam/SpEffect/EquipParam,
  а не хранит/пересылает копии PARAM всем участникам. Scaling шлёт5 коэффициентов;
  cache хранит адреса и исходную armor для обратимого перерасчёта. Удаление cache
  возвращает сканирование/повторное накопление множителей. Сохранить проверки
  table ownership и сброс при native table replacement.
- NPC/event lookup indices — локальные кэши, не сетевые таблицы; удаление может
  снизить RAM ценой повторного разбора scripts на игровом тике.
- Group/epoch/world generation/room serial/member incarnation/connection generation
  различают разные сущности. Ни один нельзя заменить закрытием сокета или одним
  общим ID. Roster/role подтверждения должны остаться durable и у всех участников.
- Старая ветка host-Dream сейчас не отправляет57 групп при DREAM_OWN=true.
  Она поддерживает прежнюю конфигурацию; удаление таблицы даёт небольшой выигрыш
  binary/RAM, но не сокращает сетевой поток действующего режима.

## Порядок реализации и обязательные доказательства

1. Status без мёртвых полей; revision gating; удаление обычного world_ready;
   диагностический kind5 отдельно. Tests: native contract/bootstrap + multipart
   decode обоих versions + личный лут/Dream. Не требовать новый игровой прогон
   только ради чистки неиспользуемых полей.
2. Адресация BBSC и разделение control/relay persistence. Independent3–5 clients:
   ищущий/допущенный/играющий/выходящий, stalled ACK, replacement connection,
   crash ingress-before-apply. Проверить, что idle roster не блокирует relay,
   но продолжает участвовать в согласовании роли по принятой политике.
3. Delta/unchanged snapshots и dirty file writes. Baseline loss/reorder/late chunk,
   map/dungeon/load change, новый гость, rejoin, переполнение очереди, native
   save failure/crash и replay pending. Для storage-правки нужны именно тесты
   затронутого восстановления, общие полные suites не нужны.
4. Только после профиля — compact consensus wire и sparse backups/кэши. Sparse
   own-world требует доказать, что native load не меняет незахваченные группы.

Перед/после считать: frames/bytes по типам и адресатам, retransmits/ACK latency,
fsync count/bytes/time отдельно control и relay, изменённые/повторно записанные
группы, stable/changed snapshots, размер RAM caches и tail latency game tick.
Процент улучшения общей производительности без таких замеров не установлен.
