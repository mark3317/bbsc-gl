# Вылеты при повторной загрузке Соборного округа после смерти

Прогон Амелии `amelia-p2-three-20261109-000428`, BBSC из дерева
на `c670391` с локальными правками, три профиля на одном ПК.
Аварийные логи в родительском
`out/coop-dev/runs/20261109-0012-p1-p2-crash/pc`, П1 в `game-7`,
П2 в `game-14`, П3 в `game-21`. Код и сейвы при разборе не менялись.

## Что сравнили

| МСК | П2, хост | П1, гость |
| --- | --- | --- |
| Около 00:09:47 | Запрос `2402950` в 00:09:47.005, прибытие в 00:09:52.106 | Запрос той же точки в 00:09:47.038, прибытие в 00:09:52.377 |
| Около 00:10:48 | Скрыта копия П3 в 00:10:48.162 | Скрыта копия П3 в 00:10:48.151 |
| Следующая смерть | Запрос `2402950` в 00:11:50.727, exit=3 в 00:11:52.385 | Запрос `2402950` в 00:11:57.428, exit=3 в 00:11:58.811 |

П3 запросил переход в Сон охотника в 00:10:48.131 и остался в комнате
до потери остальных участников. На обоих клиентах в аварийной
загрузке виден один запрос с тем же ID точки, карты и ритуала, что
и в успешной. В обоих стеках уже выполняется выгрузка старой сцены.
Нативный запрос `0x013cdf30` подбирает параметры точки, затем
вызывает тот же `0x013cde30`, который поднимает флаг загрузки при
обычном возрождении. Журналы не связывают смену карты П3 с записью
в два повреждённых поля.

## Какие ссылки уже повреждены при выгрузке

Разбор по `out/exit-study.elf`. Оба загружаемых сегмента и таблица
релокаций совпали с сегментами установленного `game/eboot.bin`.

- **П1.** `0x155b260 → 0x18dab70 → 0x18f2c8d → 0x18bb0e0`
  удаляет персонажа и освобождает его модули из `ChrIns+0x3b0`.
  Деструктор `0x1a74cb0` берёт модуль из слота 8. В `0x1a74ce5`
  он читает его vtable из `[0x1027a65ae0]`, затем в `0x1a74cec`
  вызывает `[rax+8]`. Значение `rax=0x05335990` совпадает со
  смещением штатной vtable. Оригинальный конструктор в `0x18ba767`
  вычисляет полный адрес через RIP и записывает все восемь байт.
  При штатной базе порта `0x800000000` ожидается `0x805335990`.
  Релокация слота `0x05335998` указывает на `0x1a5d8a0`.
  Упавшая инструкция видит только нижнюю часть адреса таблицы.
- **П2.** `0x1548080 → 0x204e5bc → 0x204aea3 → 0x204b0d7`
  освобождает объекты диалогов старой сцены. Деструктор
  `0x203ab70` (слот 0 таблицы `0x0535aab0`) читает внутреннюю
  ссылку из `[0x1013923ec0+0x40]` и передаёт её в `0x1001720`.
  Значение `0x00000000f84f7980` ненулевое, но чтение `[rax+8]`
  в `0x1001727` падает. Верхние 32 бита тоже нулевые. Исходное
  полное значение ссылки из журнала восстановить нельзя.

Обе ошибки видны на чтении уже неверных ссылок. В логах сохранены
регистры и стеки, данных о записи, изменившей поля, нет. По этому
снимку нельзя отличить частичную перезапись от использования
памяти объекта после освобождения или подтвердить общий источник.
Предупреждения кэша текстур были и при успешной игре. Совпадающих
событий Windows/WER о сбое GPU в аварийном интервале нет.

## Повтор с записью источника

В Windows-порте после совпадения с одной из двух аварийных инструкций
журнал выводит `Teardown pointer` с адресом **самого поля**, его значением,
базой игрового образа и потоком. Для П2 дополнительно проверяется адрес
возврата в деструктор диалога. Строка `TTD query` содержит готовый запрос
по восьми байтам поля. Порт вычисляет адрес заново из регистров при
каждом вылете.

1. Запустить П1 и П2 с `BB_WRITE_LOG=1` из окружения ярлыков. П3 запустить
   обычно. Для этого нужна сборка обновлённого `bb-probe.exe`.
2. Повторить успешное возрождение втроём. До ухода П3 в Сон записать
   отдельные трассы П1 и П2 через TTD из WinDbg. Нужны PID именно
   `bb-probe.exe`. В его командной строке аргумент `--user` различает
   профили. Из каталога для нового прогона выполнить в отдельных
   окнах PowerShell с повышенными правами для обоих процессов.
   `$ttdExe` должен указывать на `TTD.exe` из WinDbg:

   ```powershell
   & $ttdExe -out P1.run -attach $player1GamePid
   & $ttdExe -out P2.run -attach $player2GamePid
   ```

   Дождаться начала обеих записей, затем отправить П3 в Сон и повторить
   смерть П1 и П2. Если процесс выжил, остановить его запись через
   `ttd.exe -stop <PID>`. TTD пишет весь процесс в выбранном интервале,
   может замедлить игру и занять много места. Записи хранить локально,
   так как в них есть содержимое памяти процессов.
3. Открыть каждую запись в WinDbg. Выполнить `TTD query` из журнала
   соответствующего профиля. По результату выбрать запись, изменившую
   поле на аварийное значение. `IP` и `ThreadId` покажут инструкцию и
   поток. В позиции `TimeStart` проверить инструкцию и стек. Если
   нужное значение было в поле до начала записи, следующая трасса
   должна начинаться раньше.
4. Сопоставить с `Write log: pointer field`. Журнал GPU выводит источник,
   диапазон, поток и время до вылета, только если диапазон перекрывает
   найденное поле. `matches=0` означает отсутствие пересечения в
   сохранившейся части журнала. `dropped` показывает пропуски при
   одновременной публикации. Запись GPU-кольца сделана перед операцией
   и сама по себе не доказывает, что операция завершилась. Кольцо
   охватывает только уже журналируемые операции порта.

На стенде проверены оба места падения, отбрасывание чужих инструкций
и вызывающих функций, частичное перекрытие поля и режимы GPU 0/1/2.
Игра с этой диагностикой ещё не запускалась.

[поиск записей в память](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/time-travel-debugging-memory-objects).
