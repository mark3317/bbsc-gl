### Полная цепочка времени

Здесь адреса явно разделены: **image offsets** используются в runtime/ELF,
а **PS4 VA = image offset + 0x400000** — в XML.

1. Патч PS4 `0x02418E3D` задаёт шаг задачи мира по времени кадра, с границами
   пресета. При 50 FPS и цели 60 это 0.020 с.
2. Native `image+0x00F88CC2` перед диспетчеризацией задач вызывает
   `image+0x0103F9F0`. Оригинальная функция копирует `step_info+8` в собственный
   current-step движка: **image+0x054B7E08**. Это штатный источник текущего
   игрового времени, не новое хранилище мода. Прямой call xref к writer один.
3. ChrCtrl `image+0x01514AD8..0x01514B2F` передаёт личный шаг персонажа из
   `chr->modules(+0x3B0)->time(+0x90)->dt(+0x1C)` в SprjChrPhysicsModule.
   `image+0x01A4A844..0x01A4A881` формирует dt и обратный dt, а
   `image+0x01A4B968` передаёт этот step-info в оригинальный
   `LtCharacterProxyIntegrate`, `image+0x00B2F010`. Внутри proxy шаг читается,
   например, на `image+0x00B2F5DA`, перед расчётом контактных ограничений.
4. **Отдельная ветка Havok world оставалась фиксированной:**
   `image+0x017F9B71` записывает 1/60 в `rbp-0x48`. Этот же step-info
   передаётся без пересчёта на `image+0x017F9C35` в physics-world step
   `image+0x00B5A2E0`, затем finish `image+0x00B5B100`.
   Поэтому после просадки character proxy и мир движущихся collision bodies
   расходятся по времени; проблема общая для лифтов, а не конкретного EMEVD
   события или роли. У Uncap есть другой cave, но его верхний предел 1/60
   тоже расходится с задачей при длинном кадре.

Дополнительное read-only наблюдение живой установленной игры, до её закрытия
пользователем: у П1 current character dt менялся, например, до 0.019942 с,
тогда как установленная инструкция Havok оставалась `mov [rbp-0x48],1/60`.
Данные `live-steps.json` не являются покадровым trace конкретного провала:
координаты в этом коротком наблюдении стояли на месте. Позднее оба процесса
оказались завершены; агент их не останавливал.

### Исправление

Parent `scripts/patches.py:physics_frame_step` заменяет только 15-байтовый
блок построения physics step-info: мёртвую нулевую запись в `rbp-0x40`
(следующая инструкция всё равно заполняет поле) и fixed dt. Теперь EAX
читает **native current-step**, затем записывает его в `rbp-0x48`; RAX
сразу перезаписывается прежней следующей инструкцией. Регистры SIMD,
флаги, исходный task timer и параметры персонажа не изменяются.

Применяется после FPS preset writes, включая 60/90/120/144/Uncap. Для 30 FPS
и отсутствующего ELF изменений нет. Перед заменой проверяются четыре
независимых участка исходного ELF: consumer, native writer, вызов writer
до dispatch и передача готового step-info в hkpWorld. Любое несовпадение
отключает correction целиком. Внешний FPS preset по-прежнему заменяет весь
встроенный набор вместе с correction через существующий `with_external`.

Нет новых dt-констант, storage slots/caves, настройки, FPS cap, поправок
координат/телепортации, выключения коллизии или изменения файлов игры.
Physics получает уже вычисленное игровое время с родными ограничениями.

### Проверки

- `tests/test_physics_frame_step.py`: **4/4 PASS**, Windows. Читается
  оригинальный ELF, копируется в отдельную executable fixture memory;
  реально исполняются patched native producer, **original native writer**
  и original/corrected consumer. Игра для этого не используется.
- Для всех пяти пресетов проверены номинальный кадр, просадки 1.2x/1.8x,
  70 мс и защитные входы таймера. Old negative control обязан воспроизвести
  dt drift; после correction оба выходных float побитно равны. Конкретно
  50/60: раньше task20 мс / physics16.67 мс, теперь20/20.
- Прямая передача native dt0 и scaled dt0.007 также сохраняется без
  повторного вычисления; каждая несовпавшая guard запрещает всё исправление.
- `test_patches.py`: 50 checks,49 PASS/1skip; включая FPS fingerprints,
  масштабирование пресетов и замену набора внешними патчами.
- Проверки доказывают исправление конкретного расхождения часов на
  исполненном native коде. Они не заменяют игровую поездку и не доказывают,
  что любой возможный провал на платформе имеет только эту причину.

Согласующийся независимый источник: в
[bbhost frame_rate.cpp](https://github.com/droogie/bbhost/blob/master/src/engine/frame_rate.cpp)
`kFrameTimeSites` отдельно исправляет тот же fixed hkpWorld step на elapsed
frame step. Здесь использован оригинальный native current-step, без его
scratch-slot или переноса остальных изменений bbhost. Первичный код получен
для сравнения и сохранён в parent run; адреса проверены по своему ELF.

- `0x0243485A/7E/B3`: шаг структуры таймера `+0x18` фиксирован 1/60 с.
- `0x02434CF0`: native таймер сохраняет в `+0x264` разницу timestamps,
  предварительно разделённую на коэффициент преобразования времени.
- Патч `0x02418E3D`: при базовом шаге 1/60 вычисляет
  `min(max(timer[+0x264], timer[+0x18]), 1/30)` для передаваемого

- В production preset 96 отдельных writes заменяют оригинальные float
  1/30 на 1/60. Это число writes, не число независимых физических систем:
  некоторые перекрываются последующими машинными инструкциями патча.

## Вывод и граница доказательства

Главный кандидат — неодинаковый учёт просадок в обновлении движущегося
объекта/персонажа/контакта из-за смешанных часов FPS-патча, усиленный
длинными кадрами. Он согласуется с зависимостью от отношения фактического
FPS к пресету и с сообщением о любых лифтах/обеих ролях. Узкое место
расследования: пока не прослежен именно native путь перемещения платформы
и переноса стоящего на ней персонажа. Нельзя объявить причинную связь
доказанной, указать виновный конкретный вызов или величину отставания.

Логи не содержат покадровых координат/скорости платформы, контакта опоры,
фактического шага character controller и момента его отрыва. События
рычагов/плит и DEATH эту недостающую информацию не заменяют. Предыдущий
случай нижней плиты Ярнама — другой симптом, объединять его с этим нельзя.

Старый `TickBbscFrameRate` — лишь диагностический счётчик: 50 и 60 относятся
к одной полосе, предупреждение есть только выше 64. Его комментарий
про uncapped FPS прямо обозначен HYPOTHESIS и текущий случай не объясняет.

Для доказательства нужен ограниченный trace native обновления платформы
и character support в одной поездке: оба dt, transforms до/после, состояние
опоры. Сопоставить стабильные 60 и просадки; проверить обе роли. До этого
нельзя безопасно заменять все временные константы или принудительно
приклеивать игрока. Отдельный no-deltatime пресет меняет скорость игры
при просадках и не является готовым исправлением.

Сейвы, игровые assets, настройки и процессы не изменялись; commit/push нет.
