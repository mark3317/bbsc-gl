## Как работает существующий путь

1. Оригинальные EMEVD события управляют рычагами, проверяют регион и
   устанавливают постоянный флаг либо завершают своё событие. Проверенные
   события не вызывают SetNetworkSyncState(false).
2. Native channel31 передаёт продвижение событий между игроками в одном
   месте (World::ChannelPolicy/Routes, BbscWorldPacketSend). События
   разблокировки не считаются личными в production IsBbscPersonalMapEvent /
   BbscIsolatedNativeEvent. Они проходят оба штатных отправителя и приёмник.
   Native remote pending-step может продвинуть событие при локально ложном
   условии — например, когда второй игрок сам не стоит в unlock-регионе.
3. BbscWorldCaptureFlags включает постоянные unlock flags в обычные kind1
   группы снимка. TickBbscWorldSnapshots публикует снимки владельца локации;
   координатор принимает их и пересылает. Это существующий путь, добавлять
   новый тип сообщений для него не нужно.
4. BbscWorldApplyFlags устанавливает эти биты для хоста/гостя; существующий
   аддитивный merge не даёт старому снимку закрыть уже разблокированный лифт.
   Владельцу не применяется его задержанное эхо; неполные снимки не допускаются.
5. Гость в другой локации не получает текущее продвижение чужого EMEVD в свой
   исполняющийся скрипт. Снимок сохраняется по scope; при входе в нужную локацию
   GuardBbscWorldBootstrap ждёт готовности и применяет флаги до её событий.
   Это же используется при позднем подключении. Координатор принимает флаги
   обычных карт и вне своей текущей локации.

Таким образом, по исследованному коду и fixture/native проверкам отдельная
рассылка дублировала существующее распространение unlock-прогресса. Это не
доказывает отсутствие любого игрового бага с рычагами/плитами.
