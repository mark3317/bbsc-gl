## Вывод

Более нативный путь возможен как направление разработки. Обычный подбор уже
использует родные функции игры; недостающая часть — создание личной добычи врага
и надёжная доставка права на неё при смерти гостя. Переключать весь клиент в роль
хозяина не требуется. Простое отключение BBSC-очереди/award hook не решает задачу.

Нужно различать:

1. Смерть врага и право игрока на добычу.
2. Бросок лота и создание предмета на теле/в мире.
3. Подбор по кнопке и добавление в локальный инвентарь.
4. Сохранение результата при загрузке/выходе/краше.

Текущая автоматическая выдача на убийстве и создание подбираемой добычи имеют
разную семантику. Для перехода на подбор нельзя автоматически считать выданным
предмет, который лишь появился на теле.

## Проверенный native control flow

Исследован `../../out/exit-study.elf`, сегменты прочитаны по ELF program headers.
Игровые файлы и сейвы не изменялись.

- `bbsc_patch_tables.h`: ShowTreasure/ShowTreasureShare, SpawnOwn/CreateOwn,
  PlaceTreasures/PlaceTreasuresAway, PickupAsHost/GiveToGuest и MarkTaken уже
  разрешают личные сокровища и штатный подбор гостем. CreateOwn после создания
  рассылает предмет только при native state 3; гость state 6 остаётся гостем.
- Подбор: `0x017D8570` → `0x017D89F0`, локальный инвентарь. Включать заново
  скрытые предметы нельзя: доступность принадлежит родной логике сундука/события.
- `AwardItemLot 0x017DDC50`: `0x017DDC64` копирует EDX в R14D. Вычисление
  разрешения учитывает session state 6, away-state `+0x98`, own-world `+0x1592`
  и таблицу типов персонажа. Затем в `0x017DDD2F..0x017DDD44` при AL=0
  выполняются `xor r14b,1` и переход к выходу, только если результат равен нулю.
  **Аргумент EDX=0 проходит эту ветку даже при AL=0; EDX=1 — нет.**
  Поэтому имя параметра `forced` в typedef не доказывает, что значение 1 обходит
  ограничение. Изменять 0 на 1 ради разрешения гостя нельзя.
- Эта ветка исполнена настоящими байтами ELF в искусственной памяти для всех
  четырёх пар AL/аргумент. Дальнейшая выдача целиком этим тестом не исполнялась.
  Внутри native award подтверждён вызов give `0x017D89F0` в `0x017DE336`.
- `BbscGuestAwardHook` перехватывает функцию выше: обычные лоты гостя пропускает
  мимо оригинального тела и выдаёт через `GiveBbscGuestDrop`. Лоты самоцветов/рун
  уже допускает в native award; есть fallback для гарантированного лота без выдачи.
  Историческое «award не выдал» не устанавливает конкретную блокирующую инструкцию:
  разрешающая ветка выше сама по себе не доказывает прохождение всей выдачи.
- `GiveBbscPickedLotEntry` временно обнуляет веса остальных записей общего лота
  и вызывает native award только выбранной записи. Для будущего native-пути
  лучше локальный результат броска без временной правки общей PARAM-строки;
  реентерабельность/параллельный читатель такого изменения здесь не доказаны.

## Случай Юри в текущем прогоне

Логи Player1/2 `user/run_20261105_022631.log`: П2 PartyGhostDeath02:54:33.658;
П1 +5453 echoes02:54:33.723; П2 revived02:54:37.901. Выдача lot59000/1120
гостю не записана. Метаданные открытого файла показывали length0, но чтение файла
возвращает текущий текст: нулевой размер в listing не означает отсутствие лога.

`NoteBbscGuestEnemyDeath` ставит лот в память при входе в kill-reward hook,
до родного кода. Сам native kill reward содержит проверку HP локального игрока
`0x018C5103 / jle 0x018C59A6`; это не доказывает отсутствие входа в BBSC hook.
Постановка/отбрасывание конкретного лота в релизном логе не отмечаются, поэтому
потеря очереди и неполучение самого death callback пока не различены.

## Ошибочные случаи и границы проверки

| Сценарий | Результат анализа / необходимое правило |
| --- | --- |
| Живой гость, один callback | Production queue fixture выдаёт один раз |
| Гость мёртв | Production fixture: очередь очищается, предмет не выдан, после оживления потерян |
| Загрузка | Та же подтверждённая потеря |
| Уже вышел из мира хоста | Та же потеря; перенос домой должен сохранять личное право, без переноса в другого персонажа |
| Global state временно недоступен | Та же подтверждённая потеря |
| Оставить очередь при раннем выходе | Одноразовый TakeBbscWork уже поглощён: требуется reschedule, иначе очередь спит до следующего убийства |
| Убрать изъятие вообще | Без отметки завершения повторная обработка выдаёт снова; нужен ack успешного результата |
| Два гостя, разный порядок подбора | Отдельный локальный предмет/receipt каждого; подбор одного не удаляет чужой |
| Повторный callback / reinsert / повтор сетевого пакета | Нужен ключ конкретной смерти, не просто lotId или указатель актёра |
| Респавн обычного врага | Новая смерть вправе дать новый расходник; дедуп только по lotId заблокирует обычную охоту |
| Тот же номер карты другой чаши | Ключ включает реальную dungeon identity; иначе чужая добыча или ложное подавление |
| Одновременно native тело и выдача BBSC | Один производитель результата; нельзя оставлять оба для одного предмета |
| nameId0 + флаконы/пули | Текущий name-based guard не исключает дубль; происхождение награды должно быть явным |
| Смешанный лот / пустой бросок | Один бросок; отсутствие предмета — допустимый результат; fallback не должен перебрасывать |
| Уникальный лот / личный NPC | Сохранить receipt и собственные prerequisites; replicated смерть скрытого NPC не даёт право на награду |
| Закрытый сундук / скрытый treasure | Нельзя глобально выставлять pickable; родное Enable/Disable сохраняется |
| Полная сумка / лимит / хранилище | Подтверждать результат native add/переноса; текущий ручной goods add при отказе не создаёт долг |
| Смерть → тело исчезло / загрузка карты | Native spawn сам по себе не гарантирует повторное появление невзятого лота; требуется решение по сохранению |
| Краш между выдачей и квитанцией | Нужна сверка результата без повторного броска и без восстановления потраченных расходников |
| Окно награды, мёртвый игрок | Проверка native OK проходит для живого гостя и отказывает на loading/dead; выдача и показ окна имеют разные моменты готовности |
| Более64 лотов до обработки | Текущая очередь ограничена64, остальные молча не ставятся; native переход не должен сохранить этот предел как потерю |
| Поздний вход после убийства | Не выдавать все старые награды хоста; личный pickup/заслуженная смерть и инвентарь хоста — разные источники |

## Направление реализации

Сначала добавить наблюдение producer/filter смерти и native loot object: map/entity,
локальная роль, guest eligibility, lot, результат броска, native ID предмета,
причина отказа и фактическая доставка. Нужен живой и одновременно умерший гость,
хотя бы два гостя, а также nameId0 с пулями/флаконами.

Затем выбрать **один** путь создания личной добычи для конкретной смерти:
локальное штатное создание из штатного броска с сохранением host-only broadcast.
Подбор оставить существующему take→give, права гостя менять только внутри
добычи. Новый путь включать отдельно; fallback BBSC для той же смерти исключить.
Простой глобальный isGuestDrop или смена роли персонажа недостаточны.

Прямой native award расходников — отдельный, более узкий эксперимент: пропустить
точно определённый вызов через существующий hook, сохранить NPC/повторные guards,
проверить add и receipt. Это проверит выдачу без ручного AddItem, но по-прежнему
будет автоматической наградой, а не предметом на теле. Нельзя выключать весь
hook: в нём также личные разговоры, комплект и защита повторной выдачи.

Надёжное ожидание смерти/загрузки остаётся нужно независимо от способа выдачи.
До полноценной реализации нельзя заявлять, что нативный переход исправил Юри.
