## 1. Подтверждённая ошибка: committed title intent переживает Continue

ПК: 01:10:06.075 подтверждение выхода, 06.119 save finished + Stop;
01:10:32.882 requested title directly. Далее собственный персонаж снова в
Кейнхерсте: home load 01:10:45.144, alive/own-world state0 01:10:46.833;
затем hosting state3 01:11:07.927. Но сообщения
`Continue created our own character; exit guard released` нет вообще.
После Continue также нет новой `load: completed generation` (остаются только
поколения 1/2 первого призыва). Это согласуется с потерянным наблюдением загрузки.

Цепочка в emulator/src/core/bloodborne_re.cpp:
- TickBbscPendingQuit сохраняет bbsc_title_quit перед OnReturnTitle.
- Единственное обнуление — ReleaseBbscQuitTitleAtLoad(native_finish, global).
- Оно требует native_finish, а этот флаг выставляет только hook 0x0178D9C0.
- Это multiplayer ReloadFinish: native код выставляет insertion phase +0x84=4,
  обходит список участников и заканчивает 0x015C9850; его нельзя считать
  универсальным callback завершения обычного Continue.
- TickBbscLoadState вызывается в игровом tick. Если tick пропущен на всей загрузке,
  was_loading не увидит ни одного true. Одного этого fall/rise наблюдения недостаточно.
- В итоге BbscQuitInProgress навсегда true. TickBbscPendingQuit на каждом tick
  повторно пишет menu brake=1/load wait=1, пока совпадают сохранённые указатели.
  Другие действия (reinsert, follow, recovery, новый quit) также блокируются этим guard.

После закрытия комнаты116 ПК 01:12:26.293/32.345/38.371/44.404 пишет SN-stuck-locks.
После Blank комнаты117 — 01:15:31.289/37.332/43.383/49.413/55.426.
Это не доказывает повторную запись Lua извне: ReleaseBbscLeaveLocks и
ReleaseBbscDeathLocks сразу возвращаются при BbscQuitInProgress. Watchdog пишет
`released` ДО вызова этих функций, а TickBbscSessionExit пишет cleanup complete,
хотя снятие блокировок вообще не выполнялось. Есть одновременно реальный stuck
intent и ложноположительная диагностика успешного recovery.

Куда переносить обработку:
1. Отделить session-disconnected от title-entered и нового own-character-ready.
2. Снимать title intent на подтверждённом создании/готовности НОВОГО собственного
   персонажа после посещения title, с generation/token и привязкой к слоту/контексту.
   Для этого нужен общий native путь Continue/character construction, не только
   multiplayer ReloadFinish и не только polling global+8. Конкретный новый native
   адрес нужно сначала проверить на ordinary Continue; в этом разборе он не установлен.
3. Выполнить это до TickBbscSessionExit и до journal/reinsert/follow обработки.
4. Не снимать guard просто на state0 или произвольном respawn: первый state0 ещё
   принадлежит завершаемому миру. Не решать ошибку таймером или разблокировкой в title.
5. Release helpers должны возвращать released/deferred/no-op; сбрасывать
   recover_session_cleanup только после фактического выполнения. Watchdog должен
   сообщать skipped/deferred, если защитный guard не дал сделать работу.

Текущий test_menu_quit напрямую вызывает ReleaseBbscQuitTitleAtLoad(true,...).
Он проверяет predicate, но не доказывает, что настоящий Continue выдаёт это событие.
Нужна проверка пути от настоящего callback и пропущенного игрового tick.

## 2. Отдельно: Stop занимает 26–30 секунд; отмена гоняется с завершением

ПК: Stop 01:10:06.119 -> state0/title 01:10:32.882: 26.763 s.
Ноут: Stop/save finished 01:11:46.713 -> LeaveRoom 01:12:16.723: 30.010 s.
Наш cancel сработал 01:12:16.703 — за 20 ms ДО вызова LeaveRoom!
State0 на ноуте отмечен 01:12:17.523; гостя отправил домой только safety net
01:12:32.797 (15 s спустя), вместо запрошенного меню.
На сервере room116 guest leave22:12:16.802, host leave/destroy22:12:16.900:
задержка возникает ДО отправки LeaveRoom, не в обработке сервером leave.

Перед обоими Stop LogBbscQuitQueue: count0/head0. Native eboot read-only проверен:
StopRequest 0x01ED07A0 переводит +0x124 в7, затем через 0x00C8ED70 и
0x00C98070 добавляет task kind0xC(reason FF000023) через 0x00CBACA0.
Controller pointer берётся из manager+0x18; список end +0x10/count +0x18
подтверждается native scheduler. Поэтому версия «уже стоявший повторный summon
держал очередь» НЕ объясняет эти два снимка. Это снимок перед Stop, без mutex:
он не исключает конкурентного enqueue между наблюдением и постановкой Stop.
Точная native стадия, потратившая время, пока не доказана. Есть смысл исследовать
сам task0xC, его подоперации, callbacks и timeout; нельзя выдавать таймер за установленную причину.

Порядок для исправления:
- Save остаётся до Stop. Engine cleanup не вызывать из save-result callback.
- После принятого Stop не отменять пользовательский intent так, будто разрыва
  не было: команда уже отправлена и не отзывается CancelBbscPendingQuit.
- Завершение получать из game-thread обработки native disconnect completion;
  callback другого потока только ставит событие с session-generation.
- При медленном Stop оставить intent в стадии disconnecting, сообщать задержку;
  при завершении идти в title. Timeout должен переводить в explicit recovery,
  а не запускать конкурирующий home fallback. Простое увеличение 30 s не исправляет причин.
- Для точной диагностики нужны timeline enqueue/start/phase/completion task0xC,
  состояние controller и native Return/Stop result; одного queue-head ДО Stop мало.

## 4. Три двойные загрузки и позднее восстановление ключей

Во всех трёх случаях после первого summoned reload идёт kept-death/reinsert и

После cover fade ПК01:09:52.012 восстановление13 типов K2 только01:09:52.604;
ноут01:11:44.137 ->44.625 и01:13:09.808 ->10.338 (по7 типов).
Все записи говорят put back; постоянная потеря этими логами не подтверждается.
TickBbscItemLedger ждёт3 s после load и затем проверяет раз в секунду.
TickBbscLoadCover использует другие критерии и потому открывает мир раньше.
RESPAWN-guest-changed на ПК дважды восстанавливает2102961 ->2502950.
K3-repeat lot10040 сознательно допускает повтор для отсутствующего/неуникального
предмета; это не доказанная выдача дубликата уникального ключа.

Предложение: единый post-load readiness barrier для финальной (а не промежуточной)
загрузки: персонаж/инвентарь готовы -> reconcile role/origin/respawn -> флаги мира
до зависящих от них map events -> ключи после последнего native inventory reset ->
placement/reinsert ready -> fade. Сохранить периодическую сверку как страховку.
Нельзя просто передвинуть CheckBbscTripItems в ранний ReloadFinish: комментарии и
защита T5 прямо учитывают более позднее удаление предметов движком. Нужна верификация
последнего reset/готовности inventory, отрицательные сценарии перехода и отмены.
Убирать вторую загрузку без проверки освещения не предложено как готовый безопасный фикс.

## 5. Повторный merge прогресса — следствие незавершённого commit

После Continue ПК пишет after-home-load merge каждую секунду01:10:50–01:11:...
Код TickBbscSharedProgress сначала Restore/Merge, затем ApplyBbscTalkJournal;
если тот false, следующий tick снова делает Restore/Merge.
ApplyBbscTalkJournal запрещает свой native save при BbscQuitInProgress — stale
intent из пункта1 блокирует завершение. Это сохраняет журнал, но создаёт вечный
цикл. Нулевые boss/bits в строках не доказывают поломку мира, зато commit не завершён.

Нужно отделить apply/reconcile от commit acknowledgment: один применённый revision
+ generation, затем ожидание нужного native save; повторно применять только при
новой ревизии/загрузке/обнаруженном расхождении. Сначала устранить stale quit guard.
Это не основание удалять pending-файлы или вручную править сейв.

## Приоритет дальнейшей работы

1. Универсальное native подтверждение нового персонажа после title; исправление
   stale quit intent и правдивость release/cleanup diagnostics.
2. Сохранение exit intent после принятого Stop, разграничение slow/failure/completed;
   точечная диагностика native task0xC вместо гипотезы о старой очереди.
3. Один session-end arbiter для title/home/stay, watchdog только на потерю события.
4. Барьер final-load readiness и apply/commit revision для журналов.

Требуемые проверки: Continue с отсутствующим multiplayer ReloadFinish, пропуск
всех tick на загрузке, смена slot/context; stop completion на границе30 s,
после30 s и duplicate callback; kick/peer gone/quit during load и single transition;
поздний inventory reset и commit acknowledgment другой generation. Реальный
игровой контроль необходим, fixture сам по себе не закрывает баг.
