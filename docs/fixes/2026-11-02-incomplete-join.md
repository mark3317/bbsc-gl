## Почему LookupOnlineId отвечает Invalid

Клиент `gpu/bbnet/vendor/shadps4/shadnet/client.h` задаёт команду 41;
`client.cpp::LookupOnlineId` отправляет length-prefixed protobuf с npid.
Текущий серверный checkout `out/shadnet-p2p` закреплён сборщиком
`packaging/windows/build_coop_server.sh` на 5a849a192fd4450593c57b10697316ac324c856e
На момент чтения checkout содержал два применённых локальных патча
(STUN и profile directory).
В его `src/protocol.h`, `src/client_session.cpp` и `src/shadnet.proto`
обработчика/сообщений LookupOnlineId нет. Аутентифицированная команда 41
попадает в default: `Unknown command`, `ErrorType::Invalid` (2).
Эти два packaging-патча поддержку lookup не добавляют.
В конце диагностики в рабочем дереве параллельно появился новый
`0006-lookup-online-id.patch` и тест `test_lookup_online_id_protocol.py`,
добавляющие поддержку команды. Они не созданы и не проверены в этой работе;
описание отсутствующей команды относится к прочитанному server checkout
до применения нового патча, а не к будущей сборке со всеми патчами.

На клиенте `NpHandler::OnLookupReply` превращает Invalid в
`ORBIS_NP_COMMUNITY_ERROR_BAD_RESPONSE`; `sceNpLookupNpId` передаёт этот
результат в completion запроса. Это конкретная несовместимость исходников
поставляемого сервера и клиента. Состав действующего VPS в этой проверке
не читался; серверный Unknown command 41 во время эпизода не получен.
Поэтому это объяснение воспроизводимого ответа данного server checkout,
а не доказанная первопричина каждого зависшего входа из архива.
Установить причинность можно сравнением неудачной и успешной попытки
с результатами lookup и native join completion, после поддержки команды
в действующем сервере. Подмена Invalid на успех с выдуманным NpId недопустима.

## Что означает 0x8001000100000000

Предыдущее название «native rejection» описывало наблюдаемое закрытие,
но не доказанное содержание кода. Новая статическая проверка уточняет:

- `0xC8DD60`: при наличии объекта вызывает его virtual +0x38, передавая
  жёстко заданный `0x8001000100000000` (movabs в 0xC8DD8B).
- `0xC9B6E0`: обходит список объектов +0x80..+0x88, передавая каждому
  тот же жёстко заданный результат через `0xCA06B0`, затем переключается
  на phase `0xC9B960` (member drain при остановке).
- `0xCA06B0`: кладёт переданный результат в queued task +0x30 и ставит
  его через scheduler `0xCBACA0`.
- `0xCD89C0`: записывает переданный результат в object +0x68, ставит
  task state 11. Позднее `0xCD8EF2` переводит в state 13; закрытие
  `0xCD8F29` выполняется после ожидания cleanup `0xCB2B00`.

Следовательно, значение используется как общий результат отмены/teardown,
а task 13 — поздняя фаза закрытия. Это не конкретный код NP lookup,
аутентификации или отсутствия сети. Формальное имя native enum не установлено.
По значению в task 13 нельзя узнать первичный инициатор отмены.

Для twin 20:06:55.106 conn 29784 действительно был активен и закрыт локальной
игрой (Close SEND reason 1, затем хост получил Close). Это реальная отмена
pre-room попытки, но не доказанный протокольный отказ партнёра.
Отдельные 0x8000200700000000 и 0x80552711 этим выводом не переклассифицируются.

## Граница результата и следующая диагностика

Не увеличивать таймаут и не форсировать state 6: это скроет незавершённые
native этапы. Для установления причины нужны origin/caller результата на
входе в отмену, текущая native join phase/request, исходный completion/error
до cleanup и идентификатор lookup в предупреждении (user/pkt/target).
Нынешняя запись DeactivateConnection наблюдает уже следствие.
Сбой остаётся открытым; ни исправление входа, ни игровой результат не заявлены.
