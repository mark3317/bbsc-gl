## Прогон 23:45–23:50: регрессия входящего answerer

Архив investigate-20261101-2345. Обе машины загрузили DLL built 23:38:33.
Онлайн-лог ноутбука уже ротирован в last_run.1.log после следующего запуска;
собран как laptop-game-online.log. Последний last_run.log был другим запуском.

В 23:46:37.960 клиент создаёт answerer 8340, далее 8341 и на каждом Offer
новый connection ID, сразу `ignored: no connection ... not activated`.
ESTABLISHED нет. Хост закрывает 32104 в 23:47:06.518 по реальному
30-секундному signaling timeout 80552711; native hook фиксирует именно этот
результат в task13 (site CD8F29). Повтор 32105 аналогичен.

Причина — регрессия guard в 0964480: HandleControlPacket намеренно создаёт
нового answerer со state Inactive и напрямую вызывает StartHandshakeInitiator.
Новый guard ошибочно отвергал этот допустимый начальный state. Следующий
Offer не находит Inactive при поиске и создаёт ещё один answerer.
Тест ошибочно считал любой Inactive закрытым и не покрывал этот путь.

BBGL 9f26442: StartHandshakeInitiator сохраняет защиту Established/dead_fired,
но разрешает штатный начальный Inactive. Диспетчер по-прежнему отбрасывает
неактуальные queued activations для Inactive. Реальное закрытие устанавливает
dead_fired/удаляет соединение. Тест дополнен прямым incoming-answerer start,
а закрытый Inactive моделируется вместе с dead_fired. PASS.
Нативный порт перестроен; установка и игровой результат — в HANDOFF.

Книга на ноутбуке: Range rows1 в 23:47:14.911, native wait finished в
23:47:14.980 (69 ms). Завершение predicate подтверждено runtime, визуальное
исчезновение окна отдельно пользователем не подтверждено.

Сервер сообщает разные внешние порты (test 3658, twin 46006), входящие
Offers видны у клиента. Это не доказательство NAT-конфликта или firewall.
Изменять маршрутизацию/таймауты для этого отказа не требуется.

- 23:22:20.980 — игра локально активирует существующее соединение; задача

- Та же миллисекунда: игре отправлены ESTABLISHED/MUTUAL_ACTIVATED, но

  status в PENDING. established_fired остаётся true.
- 23:22:26.080 — хост вызывает DeactivateConnection (ACTIVE).

  хотя до этого получил оба события готовности. Нового ESTABLISHED в логе нет.

Это соответствует найденной гонке исходников. Последующий CheckAck зовёт
EstablishConnection, но её блок восстановления state/status выполняется только
при `!established_fired`. Поэтому соединение остаётся PENDING. Повторяемые
CheckAck и ускорение HTTP не устраняют это противоречие.

Для сравнения архив успешного входа 09:27 (runs/20261101-0926-slow-rejoin):
сервер принял claim 06:27:17.432 UTC, а test вступил в комнату 90 уже
06:27:17.667, через 235 ms. В этом journal нет промежуточного `delivered claim`.
Поэтому упрощённая цепочка «ждать следующего create и только затем native join»
не описывает все реальные пути: параллельно работает native P2P negotiation.
Поздний create не доказывает причину первичного отказа. Новый координатор
должен учитывать оба пути, а не запускать второй JoinRoom поверх первого.

Игра обменялась пакетами vport 40 в обе стороны (ошибок очереди/доставки нет).
Следовательно, утверждать, что первая попытка просто не могла связаться через NAT,
неверно. Полную причину native отказа хоста через ~5 s архив не записал.
Гонка доказана кодом и воспроизведением, её достаточность для исправления
данного игрового сценария ещё требует проверки.

Отдельная проблема управления приглашением: broker доставил claim только

## Исправление

BBGL 0964480: ProcessPendingActivations повторно оценивает текущее состояние
после ResolvePeer: готовое соединение получает идемпотентную активацию вместо
нового handshake. StartHandshakeInitiator независимо проверяет состояние под
своим mutex, закрывая окно гонки между проверкой диспетчера и вызовом функции.
Established/Inactive/dead не переводятся в SendingOffer. Отдельная revalidation
продолжает ждать ответа партнёра; её завершение не подделывается.

Bundled BBSC 9d992e8 / standalone 63b789f: четыре native call-site перед
DeactivateConnection записывают origin, conn, native task state/result/flags.
Это наблюдение, не подавление закрытия; максимум 128 записей за процесс.
Все четыре последовательности сверены с реальным eboot CUSA03173 1.09.

## Воспроизведение

tests/test_signaling_activation_race.py выполняет извлечённые production
StartHandshakeInitiator и ProcessPendingActivations с управляемым ResolvePeer.
Порядок событий: очередь pending -> ResolvePeer ждёт -> receive устанавливает
соединение -> ResolvePeer возвращается -> обработка старой задачи.
До правки assert Established падает; после правки ACTIVE сохраняется, повторных
offer/timeout нет. Проверены также поздний прямой Start после установления,
обычный старт, закрытие во время resolve, dead/missing, revalidation.
Это детерминированная проверка переходов; не стресс-тест реальных потоков/UDP.

## Более серьёзная замена polling

Нынешняя система имеет несколько независимых владельцев состояния:
native HTTP sign/search, broker claim, aimed placement через relay,
NP signaling, native vport-40 negotiation, Matching2 room, загрузка мира.
HTTP claim не является подтверждением JoinRoom, ESTABLISHED не означает
готовность native join; произвольное удержание этих состояний создаёт новую гонку.

Целевая архитектура — серверный координатор с подтверждаемыми событиями по
постоянному каналу. Это предложение, в текущую сборку НЕ реализовано:

1. Каждое включение поиска создаёт новый attempt ID. Идентичность включает
   account/character/session/attempt, а не только долговечный UserId/SessionId.
2. Advertise/Withdraw и HostOffer идут серверу как команды; сервер выбирает
   ровно одного хоста, проверяет доступность актуальной комнаты и выпускает
   Offer с attempt ID, room ID, placement, сроком действия.
3. Клиент подтверждает OfferReceived и NativeReady. Сервер доставляет события
   повторно до ACK; дубликаты идемпотентны. Порядковый номер защищает от
   старых событий после reconnect/restart/смены персонажа.
4. Native adapter работает в игровом потоке: события лишь будят допустимую
   нативную операцию. Он не выставляет state 6 и не создаёт персонажа вручную.
   Отдельно подтверждаются SignalingReady, NativeJoinStarted, RoomJoined,
   WorldReady. Таймаут относится к конкретному этапу.
5. Уход любого участника отменяет attempt и освобождает reservation/claim
   одной серверной транзакцией. После переподключения выдаётся snapshot и
   недоставленные события; завершённая старая попытка не оживает.
6. Периодические sign/search остаются только fallback для старого протокола
   и восстановления канала. Новый клиент не должен одновременно потреблять
   один claim через push и независимый HTTP POST.

Не следует заменять polling неподтверждаемой рассылкой placement: такой канал
уже есть и не управляет native join. Также нельзя просто перенести POST в
фоновый поток: он заберёт claim, который должна получить игра. Long-poll
native create может заблокировать остальную работу её matchmaking scheduler.

Миграция требует нового versioned server/client протокола и native adapter,
проверок двух конкурирующих хостов, 5 игроков, потерь/дубликатов/перестановки
событий, restart, отмены, загрузки карты и повторного входа. Её разумно вести
отдельным изменением после подтверждения базовой исправленной сигнализации;
иначе исчезнет возможность отличить сетевую гонку от ошибок нового адаптера.

## Статус

Код и целевые проверки готовы. Сборка/деплой и пользовательский прогон
фиксируются отдельно в HANDOFF. Проблема подключения целиком не закрыта.
